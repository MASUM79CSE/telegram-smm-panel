## 1. Project Context & Domain

This is a **multi-platform SMM (Social Media Marketing) Panel**, branded **"SMM Panel"** — a platform where customers deposit money into a wallet and spend it ordering services (e.g. Telegram/Instagram/TikTok/YouTube growth, organized by a `ServiceGroup` per platform) fulfilled either manually by an admin, by the platform's own automation, or by calling an upstream reseller-style provider API. Customers and admins can act through a normal web dashboard **or** through a Telegram bot — both surfaces are first-class and share identical business logic. **Project-owner decision (Phase 1.4 of `docs/IMPLEMENTATION_PLAN.md`):** this project is explicitly multi-platform, not Telegram-only — the product was rebranded from "TG Panel"/"Telegram SMM Panel" to "SMM Panel" to reflect this, and `scripts/seed.ts` seeds one demo `ServiceGroup`/`Category`/`Service` per platform (Telegram, Instagram, TikTok, YouTube) out of the box. The Telegram *bot* remains a first-class control surface regardless — the rebrand is about the service catalog's scope, not about deprecating the bot.

**Compliance stance (explicitly encoded in `models/Provider.ts`'s doc comment):** this platform is intended for legitimate, ToS-compliant services — not fake engagement, bot-follower farming, or platform-abuse automation. This is a product/business-policy responsibility enforced by what services are actually listed in the catalog, not something the code can technically prevent — worth remembering if you're ever asked to "just add a service" without scrutiny.

## 2. Origin & Major Pivots (history worth knowing)

The user explicitly redirected to **MongoDB Atlas + Mongoose** mid-project — this is why you'll see code comments referencing "the original plan's `Decimal(12,4)`" (in `lib/money.ts`) or "the original plan's queue/worker system" (in `scripts/process-orders.ts`): these are intentional callbacks explaining *why* the Mongo/Mongoose equivalent was built the way it was, not stale leftover text.
- The user explicitly said **"do it as your best choice, and make it production level, also make it safe"** — this is why security/production concerns (rate limiting, encryption at rest, audit logging, account lockout, security headers) were built in from the start rather than bolted on later, and why `docs/PRODUCTION_READINESS.md` exists as an ongoing honest checklist rather than a one-time pass.
- A Telegram bot logo (`assets/smmgo-bot-logo.png`) was generated in an earlier session for a "SmmGo" branding direction that was never actually adopted by the live bot (which is unbranded/generic — see `TELEGRAM_BOT_USERNAME` config). That file has been **deleted** during this documentation/cleanup pass since it had zero references anywhere in the code and no longer reflected any current branding decision. If bot branding comes up again, start fresh rather than assuming that asset is still relevant.
- A prior debugging session investigated a discrepancy where a user reported completing a Telegram `/order` flow but no corresponding `Order` document existed in the database. **This was never fully root-caused** — the user was mid-troubleshooting (about to retry the flow step-by-step) when attention shifted to this documentation/cleanup task. If this resurfaces: check (a) whether `/link` actually succeeded before `/order` was attempted (an unlinked user gets a silent-looking failure — actually a clear "not linked" message, but easy to miss in a chat transcript), (b) whether the wallet had sufficient balance (an `INSUFFICIENT_BALANCE` `AppError` would end the conversation with a message, not create a record — working as designed, but easy for a user to describe as "I completed the order" when they actually just answered the conversation prompts up to the point of rejection), and (c) server logs around the reported time for any uncaught exception in the conversation handler.

## 3. Key Architectural/Technical Decisions (see `docs/ARCHITECTURE.md` for full rationale)

- **One Next.js app, not separate web/bot services** — the money-moving logic must be identical regardless of entry surface; see `lib/services/*`.
- **`Decimal128` everywhere for money, never `Number`** — arithmetic only via `lib/money.ts` helpers. If you ever see a raw `+`/`-`/`*` on a balance/charge/amount field outside that file, treat it as a bug to fix, not a pattern to follow.
- **Optimistic concurrency (`Wallet.version`) *inside* MongoDB transactions**, not instead of them — a transaction alone doesn't prevent two concurrent transactions from both reading the same stale balance. This combination is the load-bearing correctness mechanism for the entire wallet system; do not remove the version check as "redundant" with the transaction.
- **Idempotency keys on `Transaction` rows for approve/refund flows** — prevents double-crediting from a retried request or an admin double-clicking Approve. If you add a new money-crediting action, follow the same pattern (atomic status-guard claim + idempotency key), don't skip it because "the UI disables the button after one click" (client-side guards are not a substitute for server-side idempotency).
- **`AppError` as the shared error vocabulary** between the web routes and the bot — if you add a new business-rule rejection, throw `AppError`, don't return `null`/a magic string, so both surfaces keep handling errors consistently.

## 4. Coding Conventions & Standards

- **TypeScript strict-mode, no `any` sprinkled around** — verified clean `tsc --noEmit` and `eslint` runs are the project's actual (if minimal) quality bar today; keep both clean before considering work "done."
- **Route handlers are thin adapters** — auth check → rate limit → validate → call a `lib/services/*` function → map result/errors to a response. Business logic does not belong directly in `app/api/**/route.ts`; if a route handler is doing anything beyond that shape, it should probably be extracted into `lib/services/`.
- **Money math only through `lib/money.ts`.**
- **All user-controlled strings sent to Telegram must go through `escapeHtml()`** (`lib/telegram/format.ts`) before being embedded in an HTML-parse-mode message — this is the injection defense for that surface; don't bypass it for convenience.
- **Notification/audit side effects must never throw** — wrap in try/catch internally (as `lib/audit.ts` and `lib/telegram/notify.ts` already do) or call sites must `.catch(console.error)` — a broken Telegram/audit/email path must never fail the primary operation.
- **Sparse unique indexes and `null` defaults don't mix** — see the `User.telegramId` callout in `docs/DATABASE.md` §4. This is a specific, easy-to-reintroduce bug if a future contributor "cleans up" the schema by adding a `default: null`. **This bug actually recurred in `Transaction.idempotencyKey` and broke order placement in production for every order after the first one in the system's history** (found/fixed in Phase 2.1 — see §7). Treat this as the single highest-value lint rule this project doesn't have: grep for `default: null` next to `sparse: true` before trusting any schema change is safe.
- **A "leave in `PROCESSING` for the worker to retry" design only works if the worker's guard actually treats that state as retry-eligible** — `dispatchOrderToProvider` originally only accepted `status === "PENDING"`, silently no-op'ing on every `PROCESSING` order the worker handed it, so `MAX_ATTEMPTS`-based retry never actually ran for any order that failed even once (found/fixed in Phase 2.1 — see §7). If you ever add another "leave it in an intermediate status for later retry" pattern, verify live (not just by reading the code) that the retry path is actually reachable, since `PROCESSING` here is overloaded to mean two different things (awaiting a human vs. awaiting an automatic retry) and it's easy for a guard clause to accidentally treat both the same way.

## 5. Known Limitations & Technical Debt (see `docs/PRODUCTION_READINESS.md` for the exhaustive, categorized version — this section is a living summary and can drift; if in doubt, trust that file's own ✅/⚠️/❌ markers per section over this list)

The highest-impact ones to keep in mind day-to-day:

- **Four layers of automated test coverage now exist**: unit (`vitest`, 201 tests, `lib/__tests__/`, pure logic + route-handler auth boundaries + rate-limiting/lockout), DB-backed integration (`vitest`, 35 tests, `lib/__tests__/integration/`, real `mongodb-memory-server` replica set, covers the four transactional money-moving service functions plus the queue-depth check), route-auth-boundary (part of the unit suite, all 44 `app/api/**` route files), and end-to-end (`Playwright`, 8 tests, `e2e/`, real browser against a real ephemeral DB). Run via `npm run test`, `npm run test:integration`, `npm run test:e2e` respectively (`npm run test:all` for the first two together). All wired into CI (`.github/workflows/ci.yml`) except `test:e2e`, which must still be run manually/locally. See `docs/PRODUCTION_READINESS.md` §15 for the full detail.
- **The background order processor is no longer single-deployment-shape-only.** `lib/services/jobs.ts` holds the shared logic, invoked two ways: the original long-lived CLI scripts (`scripts/process-orders.ts` etc., `--loop` mode, for any deployment that can run persistent processes) **or** authenticated `GET /api/cron/*` HTTP routes invoked on a schedule by GitHub Actions (`.github/workflows/cron.yml`), for this project's actual deployment target — Vercel — which cannot run persistent processes at all. Neither path has real distributed locking; running genuinely concurrent instances of either still risks redundant/racing work on the same order (degrades to wasted work, not corruption, per each job's own idempotent "re-query what's eligible now" design) — don't scale either path horizontally without adding real coordination first. A queue-depth check (`checkQueueDepth()` in the same file) now alerts (fails the scheduled GitHub Actions run) if orders pile up stuck in `PROCESSING` or `PENDING` for too long.
- **`ALLOWED_ORIGINS` is enforced** — see `docs/PRODUCTION_READINESS.md` §9 and `docs/ARCHITECTURE.md` §10 for the mechanism.
- **`AUTH_TRUST_HOST` must be `true` in production, or the entire app is unusable there.** Validated/warned-about in `lib/env.ts`, documented in `.env.example` and `README.md` §11, set in CI's build step. If you deploy this app and hit `UntrustedHost` errors, check this before anything else.
- **Running behind a non-`localhost` preview/tunnel domain** (e.g. Arena Agent Mode / E2B sandboxes) requires `next.config.ts`'s `allowedDevOrigins` and `ALLOWED_ORIGINS` (`.env.local`) to both include that domain, or every client-side form silently fails with no visible error. See `docs/PRODUCTION_READINESS.md` §9's matching entry for the full root-cause/fix/verification record.
- **2FA schema fields exist on `User` (`twoFactorEnabled`/`twoFactorSecret`) but are still not wired into the login flow anywhere.** Don't describe 2FA as a working feature to users or in marketing copy until `auth.ts` actually verifies a TOTP code. Still an open gap — nothing has changed here since it was first flagged.
- **Error tracking, performance monitoring, and order-processing queue-depth alerting are now implemented via Sentry (`@sentry/nextjs`) — this is no longer a gap.** Safe no-op until `SENTRY_DSN`/`NEXT_PUBLIC_SENTRY_DSN` are actually set on the deployment (see `.env.example`, `README.md` §8/§11). **Still genuinely open**: general-purpose custom business metrics (a Prometheus/Grafana-style pipeline) remain explicitly out of scope — see `docs/PRODUCTION_READINESS.md` §6's own "NOT in scope" callout — and Sentry's own Alert Rules still need to be configured by hand in the Sentry dashboard once a real project exists, which hasn't been confirmed done.
- **CI/CD is now implemented, not absent.** `.github/workflows/ci.yml` runs typecheck/lint/unit+integration tests/build/e2e on every push/PR to `main`. Deployment target is **Vercel**, via its native Git integration (gated on CI passing), with `.github/workflows/cron.yml` (GitHub Actions, since Vercel Hobby's own Cron Jobs are daily-only) driving the three background jobs and `.github/workflows/post-deploy-smoke-test.yml` checking `GET /api/health` after every production deploy. **Automated rollback is now implemented but opt-in**: on a failed smoke test, the workflow can automatically revert production traffic to the last known-good Vercel deployment via the Vercel REST API, gated behind the `AUTO_ROLLBACK_ENABLED` repository variable and `VERCEL_TOKEN`/`VERCEL_PROJECT_ID`/`VERCEL_TEAM_ID` secrets (see `docs/PRODUCTION_READINESS.md` §14). It is off by default and has not been exercised against a real Vercel project from this sandbox; the manual Vercel-dashboard rollback (`docs/INCIDENT_RESPONSE.md` §6.1) remains the reliable fallback either way.
- **Database backup**: Atlas Cloud Backup enablement and a real restore-to-a-new-cluster drill are still genuinely unperformed operational actions (see `docs/PRODUCTION_READINESS.md` §13, `docs/DATABASE.md` §9) — this requires Atlas console access tied to a paid tier/billing account. A restore-verification tool (`scripts/verify-restore.ts`) exists and has been checked against real production data, but not yet against an actual Atlas-restored snapshot.
- **Project is a git repository with real commit history** — this changed since this section was first written; don't assume otherwise.

- **A Mongoose `.select()` gotcha, the same *class* of mistake already documented for `ServiceProvider.populate()` in Phase 2.1 but a different specific bug:** `.select("+apiKeyEncrypted type")` — mixing a `+field` opt-in token (re-including a `select: false` field) with an ordinary plain field name in the *same* `.select()` string call — silently switches the whole query into inclusion-only mode, dropping every other field on the document (including `apiUrl`) rather than just adding the two named fields on top of the full document. This broke every refill against a real API provider with a misleading "Provider is missing API configuration" error. **General lesson: never mix a `+field` token with a plain field name in one Mongoose `.select()` call — either use `+field` alone (re-include one `select:false` field, keep everything else) or pass a full explicit field list, never both conventions together.**
- **A genuinely pre-existing bug, unrelated to Phase 3's own new code, surfaced only because Phase 3.1 was the first feature to actually exercise the affected code path:** Zod v4 forbids calling `.partial()` on any object schema that already has `.refine()`/`.superRefine()` applied — it throws `"Error: .partial() cannot be used on object schemas containing refinements"` **at request time**, not at schema-definition time, so this kind of bug can sit latent indefinitely until the first partial-update (`PATCH`) request actually exercises that exact schema. `lib/validation.ts`'s `serviceSchema` had a `maxQuantity >= minQuantity` cross-field `.refine()` (added at some undetermined earlier point, unrelated to refill), and `app/api/admin/services/[id]/route.ts`'s `PATCH` handler called `serviceSchema.partial()` — meaning **every single admin service edit had been silently 500ing**, not just `refillDays` changes, and nobody had noticed because the admin service-edit UI hadn't - **Two real, previously-undiscovered bugs found and fixed while building this suite** (both fully described in `docs/PRODUCTION_READINESS.md` §15 — not repeated in full here, only the actionable lesson):
  1. **Playwright's `config.webServer` cannot be used when the server needs env vars computed asynchronously during test setup.** Confirmed by reading `node_modules/playwright/lib/runner/index.js`: `webServer` is a plugin, and plugin-setup tasks run *before* `globalSetup`, so any `process.env` mutation made inside `globalSetup` (this suite's `MONGODB_URI`, only known after asynchronously creating an in-memory Mongo replica set) is invisible to a Playwright-managed `webServer` process — it would see `undefined`/defaults instead (observed directly: the spawned server printed `Local: http://localhost:3000`, the Next.js default, instead of the intended `3100`). **Fix pattern for reuse:** don't use `config.webServer` at all when the server's env depends on async setup work; have `globalSetup` spawn and own the server process itself (via the actual binary, e.g. `node_modules/.bin/next`, not `npm run <script>` — see next bug), wait for it to respond before returning, and kill it in the returned `globalTeardown`.
  2. **Spawning a server via `npm run <script>` instead of the binary directly leaves an orphaned grandchild process after `SIGTERM`.** `npm` spawns an intermediate shell which spawns the real process; killing just the `npm` process doesn't reliably propagate. This left a real `next-server` bound to the test port after one run ended, breaking the *next* run with `EADDRINUSE`. Fixed by spawning `node_modules/.bin/next start` directly with `detached: true`, and killing the whole process group (`process.kill(-pid, "SIGTERM")`) in teardown.
  3. **`MongoMemoryReplSet.getUri()` called with no argument omits the database name from the URI**, so any connection made without an explicit `{ dbName }` option lands in Mongoose's default `"test"` database. This suite's seeding connection originally used `{ dbName: "e2e" }` while the real app (`lib/db.ts#connectDB()`, which never passes `dbName`) landed in `"test"` — two different databases on the same replica set, so the server could never see any seeded user and every login failed with a generic `CredentialsSignin`. **Fix pattern for reuse:** always call `getUri("dbname")` with the name baked in, and reuse that exact URI string everywhere (both the test's own seeding connection and `process.env.MONGODB_URI`) rather than passing a separate `dbName` connect option anywhere.
- **Test design decisions worth remembering if extending this suite**: `components/dashboard/order-form.tsx` and `components/dashboard/deposit-form.tsx` don't associate `<label>`s to their inputs via `htmlFor`/`id` — `getByLabel()` silently fails to match; use structural locators (`page.locator("select")`, `getByPlaceholder`, `input[type="number"]`) instead, the same way a sighted user would identify the field. ## 7e. Login IP-based rate limiting — real bug found, fixed, and then tuned via the e2e suite's own feedback

Continuing the standing Task 7 instruction (scan `PRODUCTION_READINESS.md` for closeable gaps) after §7d closed the testing-section list entirely. This one wasn't on that list — it was found by re-reading §9/§12's rate-limiting claims against the actual code.

- **The bug**: `lib/rate-limit.ts` had a `login` entry in its `configs` map, and every other sensitive route (register, password reset, order creation, payment submission, ticket create/reply, API key creation, Telegram linking) actually called `rateLimit(...)`, but `auth.ts`'s Credentials-provider `authorize()` never did — confirmed by grepping every `rateLimit(` call site in the repo. A single IP could therefore attempt unlimited logins against unlimited different accounts with zero throttling; the separate per-account lockout (5 failed attempts → 15-minute lock, already implemented) only stops repeated failures against ONE account, not a credential-stuffing spray across many.
- **The fix**: extracted the provider's actual logic into a standalone, directly unit-testable `authorizeCredentials(credentials, ip)` in the new `lib/auth/authorize.ts` (needed because `auth.ts` itself can't be imported under Vitest's plain-Node test environment — it pulls in Next.js request-scoped machinery). `auth.ts`'s `authorize()` is now a thin wrapper that gets the request IP and delegates. Added `rateLimit("login", ip)` as the very first check inside `authorizeCredentials`.
- **First-pass value chosen too tight, caught by the e2e suite (not by unit tests)**: initially set `configs.login` to `[5, 60]` (5 attempts/60s per IP) — a normal textbook default. Running the full quality gate (`tsc` → `lint` → `test` → `test:integration` → `test:e2e`) surfaced a real failure: `e2e/order-flow.e2e.ts`'s order-placement test timed out inside `loginAs()`. Root-caused via the e2e run's own server log (`/tmp/e2e-server-*.log`): repeated `[auth][error] CredentialsSignin`, correlated with the rate limiter, not a real credentials/DB bug. Cause: that one Playwright run logs in as three different seeded accounts (register→login, deposit-customer, admin) from a single test-runner IP within under 20 seconds — a legitimate multi-login pattern, and a realistic stand-in for real shared-IP scenarios (office/university NAT, a household, a VPN exit node) that a naive per-IP limit will also incorrectly punish in production.
- **Resolution**: since per-account lockout already independently defends against single-account brute force, concluded the IP-level limit's only real job is catching high-volume *multi-account* credential-stuffing floods, so it can and should have much more headroom. Raised `configs.login` to `[20, 60 * 5]` (20 attempts per 5-minute window per IP) in `lib/rate-limit.ts`, with a multi-paragraph comment on that line explaining the reasoning and citing this exact e2e discovery so a future reader doesn't "fix" it back to something tighter without re-learning this lesson.
- **Test-suite knock-on effect**: `lib/__tests__/auth-authorize.test.ts`'s two real-rate-limit tests (using the actual unmocked `lib/rate-limit.ts`, not a mock) had their loop bounds updated from `5`/`6` to a `LOGIN_LIMIT = 20` constant (commented as needing to track `configs.login[0]`). This then made those two tests loop 20+ real bcrypt cost-12 compares each, which exceeded Vitest's 5000ms default per-test timeout — fixed with an explicit `20_000`ms timeout argument on both tests (not by weakening the bcrypt cost or the real-module rate limiter, to keep the test faithful to production behavior).
- **General lesson for future sub-tasks in this project**: when tuning any rate limit (or similar per-IP/per-account throttle), don't just unit-test the limit's arithmetic in isolation — run it against the e2e suite too, since e2e is the only place that exercises realistic *aggregate* request patterns from one source across a full user journey. A value that looks reasonable per-endpoint can still be wrong once real multi-step flows are considered.

## 7f. Structured logging via Pino (closes PRODUCTION_READINESS.md §3) — plus a real request-handling bug found and fixed by its own verification gate

- **What changed**: added `lib/logger.ts` (Pino-based) and `lib/security/request-id.ts` (per-request correlation id, generated once in `proxy.ts`, threaded to route handlers as a request header and to the browser as a response header). - **A real bug was found and fixed by this sub-task's own verification gate, before merge — not a pre-existing production issue.** An early draft of the request-id threading in `proxy.ts` called its `withHeaders()` helper twice against the *same original* incoming `NextRequest` object: once to attach the new request-id header (for the origin check), and again, independently, off that same original, to attach the CSP nonce header later in the function. Constructing a `NextRequest`/`Request` from another `Request` instance consumes that instance's body stream; building a *second* wrapper from the *same already-consumed* original throws `TypeError: Cannot construct a Request with a Request object that has already been used.` This only manifests when the middleware runs against a real, already-built production server (`next start`) — exactly what the Playwright e2e suite exercises and `next dev` does not reproduce the same way — so `npx tsc --noEmit`, lint, and both Vitest suites all stayed green while three of the eight e2e specs (registration, deposit submission, order placement — i.e. every flow that reaches an authenticated dashboard route) failed with `page.waitForURL` timeouts caused by the server 500ing on every request. Root-caused via the e2e run's own captured server log (`/tmp/e2e-server-*.log`), which showed the exact `TypeError` and stack trace. **Fix**: chain the second `withHeaders()` call off the already-rewrapped `requestWithId` instead of the original `request`, so the original request object is only ever consumed once. **Lesson for future sub-tasks that touch `proxy.ts` or any other code that wraps/reconstructs a `Request`/`NextRequest`**: never call a "clone with extra headers"-style helper more than once against the same original request instance — always chain subsequent wraps off the most recently produced wrapper, and always re-run the full e2e suite (not just unit/integration) after touching middleware, since this exact class of bug is invisible to `next dev` and to mocked-request unit tests alike.

## 8. Future Considerations / Maintainability Guidance

- Before adding a new money-moving action (a new deposit method, a new refund path, etc.), copy the pattern in `lib/services/admin-payments.ts` (`approveDeposit`) exactly: atomic status-guard claim → transaction → optimistic-concurrency wallet update → idempotency-keyed ledger row. Don't improvise a new pattern.
- Before adding a new Telegram bot command, put the actual business logic in `lib/services/` (or reuse existing service functions) rather than writing it inline in `lib/telegram/bot.ts`, so the website can get the same feature "for free" later if needed.
- If you introduce a real message queue/job system to replace `scripts/process-orders.ts`'s polling design, keep the existing `Order.attempts`/`lastError`/`lastAttemptAt` fields — they're queue-implementation-agnostic bookkeeping that any replacement design will still want.
- If this project starts handling regulated financial data at meaningful volume, revisit the "no retention/archival policy" gap noted in `docs/DATABASE.md` §7 before it becomes a compliance problem rather than a documentation footnote.
