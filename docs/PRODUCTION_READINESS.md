# Production Readiness

This document is an honest audit of the system against production-operations concerns: what's already implemented (with the exact mechanism), what's a known gap, and concrete recommendations for closing each gap. It intentionally does **not** describe aspirational features as if they exist — every "✅ Implemented" claim below was verified by reading the actual source referenced next to it.

For environment-variable specifics see [`../README.md` §8](../README.md#8-environment-variables). For architecture rationale see [`ARCHITECTURE.md`](ARCHITECTURE.md).

## Legend
- ✅ **Implemented** — exists in the codebase today, source cited.
- ⚠️ **Partial** — something exists but has a known limitation.
- ❌ **Gap** — not implemented; recommendation included.

---

## 1. Environment & Configuration Management

✅ **Implemented** — `lib/env.ts` centralizes and Zod-validates every environment variable, fails fast at startup (not silently at first use) if something required is missing or malformed, and specifically rejects a production deployment still running the example placeholder `AUTH_SECRET`. `.env.example` documents every variable with inline comments.

⚠️ **Partial** — there is no distinct "staging" environment configuration; the schema only distinguishes `development` / `test` / `production` via `NODE_ENV`. If you introduce a staging environment, treat it as `NODE_ENV=production` with its own separate `.env`/secrets and its own Postgres database (a separate Supabase project, or at minimum a separate database within one project — never share a database between staging and production).

## 2. Secrets Management

✅ **Implemented** — `.env.local`/`.env` are git-ignored (`.gitignore` covers `.env*`); provider API keys are AES-256-GCM encrypted at rest (`lib/crypto.ts`) using a key derived from `AUTH_SECRET`, and excluded from default query projections (`select: false`); tokens (email verify/reset/Telegram-link) are stored only as SHA-256 hashes, never raw.

❌ **Gap** — there is no integration with a dedicated secrets manager (AWS Secrets Manager, HashiCorp Vault, Doppler, etc.); secrets live in platform environment variables. This is acceptable for a small-to-medium deployment on most modern PaaS platforms (Vercel, Railway, Render, Fly.io all encrypt env vars at rest), but if you scale to multiple services/teams, consider a secrets manager with audit-logged access and automatic rotation.

**Recommendation:** rotate `AUTH_SECRET`, `TELEGRAM_WEBHOOK_SECRET`, and the Supabase/Postgres database role's password on a defined schedule (e.g. every 90 days) and immediately after any suspected exposure; document who holds access to production secrets.

## 3. Logging Strategy & Log Levels

✅ **Implemented (closed in this pass)** — every `console.log`/`console.error`/`console.warn` call site across `app/api/**`, `lib/**` (excluding `lib/__tests__/**`), and `lib/telegram/**` was replaced with a call into the new centralized structured logger, `lib/logger.ts` (built on [Pino](https://getpino.io/)). Deliberately left as plain `console.*` (see `lib/logger.ts`'s own doc comment for the rationale): `scripts/**` one-shot/long-running CLI tools (`seed.ts`, `process-orders.ts`, etc.) — they're run interactively or by a process manager that already timestamps output, and pulling in request-correlation machinery there adds complexity with no real benefit.

**Design, as shipped:**
- Production (`NODE_ENV=production`) emits newline-delimited JSON — Pino's default and fastest mode, and what every real log aggregator (Vercel, Railway, a Docker log driver, CloudWatch) expects.
- Development/test uses `pino-pretty` for human-readable colorized terminal output; Vitest's `NODE_ENV=test` run is silent by default (no `pino-pretty` worker-thread transport spawned, which would otherwise leak an open handle and slow down/flake the test suite) unless a developer opts in with `LOG_LEVEL=debug`.
- A per-request correlation id (`reqId`) is generated once in `proxy.ts` (`lib/security/request-id.ts`), forwarded to the route handler as a request header and to the browser as a response header, and threaded onto every log line a route handler emits via `requestLogger(request)` — so a support/on-call engineer can grep every log line produced while handling one specific HTTP request, or correlate a user-reported error against server logs using the id returned in the response.
- Common secret-shaped fields (`password`, `passwordHash`, `authorization`, cookies, `apiKey`, `token`) are redacted defensively via Pino's `redact` option, in case a caller ever accidentally logs a full request/user object carrying one of these keys.
- Three call patterns are used depending on what's in scope: `requestLogger(request)` wherever a `Request`/`NextRequest` is available; bare `logger` where it isn't (e.g. `lib/rate-limit.ts`'s startup warning, the Telegram bot's own event loop); and a conditional fallback (`params.request ? requestLogger(params.request) : logger`) in the one call site, `lib/audit.ts#recordAudit`, that's invoked both from route handlers and from contexts with no request in scope.

**Bug found and fixed during this pass's own verification (not present before this change; introduced by an early draft of the request-id threading and caught by the project's own Playwright e2e suite before being merged):** `proxy.ts` originally called its `withHeaders()` helper twice against the *same original* incoming `NextRequest` — once to attach the request-id header before the origin check, and again, independently, off that same original request, to attach the CSP nonce header afterward. Constructing a `NextRequest`/`Request` from another `Request` instance consumes that instance's body stream; constructing a second one from the *same already-consumed* original throws `TypeError: Cannot construct a Request with a Request object that has already been used.` This surfaced as every request hard-erroring in a real `next start` production server (i.e., exactly the environment the e2e suite exercises, unlike `next dev`, which does not build a single shared production middleware bundle the same way) — three e2e specs (registration, deposit submission, order placement, i.e. any flow reaching an authenticated dashboard route) failed with a `page.waitForURL` timeout because the server was 500ing on every navigation. Fixed by chaining the second `withHeaders()` call off the *already-rewrapped* `requestWithId` instead of the original `request`, so the original is only ever consumed once. Full verification gate (`tsc`, lint, 135/135 unit tests, 22/22 integration tests, production `next build`, and all 8 Playwright e2e specs) is green after the fix.

**Verification:** `grep -rn "console\." app lib` (excluding `lib/__tests__/**` and `scripts/**`) returns zero remaining call sites outside the deliberately-excluded scripts.

## 4. Error Tracking

✅ **Implemented** — `@sentry/nextjs` is wired up across all three Next.js runtimes: `instrumentation-client.ts` (browser), `sentry.server.config.ts` (Node.js — API routes, Server Components, the Telegram bot's request handling), and `sentry.edge.config.ts` (edge runtime, for forward-compatibility even though `proxy.ts` currently runs on the Node.js runtime by default under Next 16). `instrumentation.ts`'s `register()` loads the correct config per runtime and exports `onRequestError = Sentry.captureRequestError` to also capture errors thrown in Server Components/`proxy.ts` that don't go through a route handler's own try/catch. `next.config.ts` wraps the config with `withSentryConfig` (from `@sentry/nextjs/config`, the current non-deprecated import path) for source-map upload and the `/monitoring` tunnel route (see below).

**Deliberately a safe no-op until you configure it**: every init call checks `SENTRY_DSN`/`NEXT_PUBLIC_SENTRY_DSN` and sets `enabled: Boolean(dsn)` — with no DSN set (the default for local dev, CI, and any deployment before you create a Sentry project), the app behaves exactly as it did before this integration existed. Verified: `npm run build` succeeds with these env vars unset, and a live `next dev` run against every major route (homepage, login, admin, the three new `/api/cron/*` routes) showed identical behavior/headers before and after this change.

**What you still need to do**: create a Sentry project (the free tier needs no payment info), then set `SENTRY_DSN` and `NEXT_PUBLIC_SENTRY_DSN` (same value — the client SDK needs the `NEXT_PUBLIC_`-prefixed one to be exposed to the browser bundle) in your deployment's env vars. Optionally set `SENTRY_ORG`/`SENTRY_PROJECT`/`SENTRY_AUTH_TOKEN` to enable source-map upload (readable stack traces in the Sentry UI instead of minified ones) — safe to leave unset, the build just skips that step silently.

**Turbopack-specific fix applied**: Sentry's tunnel route (`tunnelRoute: "/monitoring"` — routes browser SDK events through this app's own domain to avoid ad-blockers) was initially intercepted and 404'd by next-intl's locale-routing middleware in `proxy.ts`, since `/monitoring` isn't `/admin` or `/api` and so fell into the locale-routed bypass group by default. Fixed by adding `/monitoring` to `proxy.ts`'s existing locale-routing exclusion list (same mechanism already used for `/admin`/`/api`) — this is the officially documented fix for this exact Turbopack + middleware interaction. Verified live: `curl -I http://localhost:3000/monitoring?o=...&p=...` now reaches Sentry's real ingest endpoint (external `via` header) instead of returning this app's own 404.

**Privacy note**: Session Replay is deliberately NOT enabled (see `instrumentation-client.ts`'s doc comment) — this app handles wallet balances and payment references, and recording user sessions (even masked) adds a privacy/compliance surface not yet evaluated. Revisit deliberately later if actually needed.

**Global error boundary**: `app/global-error.tsx` (Sentry's own recommended App Router pattern) reports to `Sentry.captureException` and renders a minimal fallback UI for the rare case where `app/layout.tsx` itself fails to render — the one class of client error `instrumentation.ts`'s `onRequestError` hook and route-level `error.tsx` boundaries can't catch, since it replaces the root layout itself. It defines its own `<html>/<body>` deliberately (cannot assume `SessionProvider`/next-intl/the CSP nonce from the real root layout are available, since those are exactly what may have just failed) and is a plain, working error boundary even with no Sentry DSN configured.

## 5. Monitoring & Observability

✅ **Implemented** — `GET /api/health` checks database connectivity via a real round-trip `prisma.$queryRaw\`SELECT 1\`` (see that route's own header comment for why this is preferred over a cached connection-state flag) and returns `200`/`{"status":"ok"}` when healthy or `503`/`{"status":"error"}` when the database is unreachable, suitable for a load balancer/orchestrator liveness or readiness probe. It deliberately does no writes and stays lightweight.

✅ **Order-processing queue-depth visibility — implemented**, closing what was previously tracked here as a gap (general request-latency/error-rate/throughput metrics collection, e.g. a Prometheus endpoint or StatsD/Datadog calls, remains explicitly out of scope — see §6 below for the exact boundary). The specific "is an order stuck in PROCESSING because the background worker died" failure mode this section called out as the most exposed one is now checked by `lib/services/jobs.ts#checkQueueDepth()` (`prisma.order.count({ where: { status: "PROCESSING", updatedAt: { lt: <15 min ago> } } })`, plus a `PENDING` backlog check) on every `GET /api/cron/process-orders` run, alerting via a `503`/failed-GitHub-Actions-run when breached — see §6 and §14 for the full mechanism, and `docs/INCIDENT_RESPONSE.md` §6.2 for the on-call response. Verified live against this project's real production Supabase database (not just the test suite): a real, temporary stale `PROCESSING` order was inserted directly into the live `Order` table and the endpoint correctly reported the alert before the probe row was deleted.

**Still a real gap, not covered by the above**: general request-latency/error-rate/throughput metrics collection (no Prometheus endpoint, no StatsD/Datadog metrics calls, no dashboard for overall system health beyond the specific queue-depth signal above) — Sentry Performance Monitoring (§6) covers transaction/latency visibility per route as a lighter-weight substitute, but this is not a general-purpose custom-metrics pipeline. See §6's own "NOT in scope" callout.

## 6. Metrics & Alerting

✅ **Implemented, with a deliberate scope decision** — rather than standing up a second, separate metrics/APM vendor, this project reuses Sentry's built-in Performance Monitoring (the same SDK/account as §4 above): `tracesSampleRate` is set in all three Sentry config files, giving transaction traces, p50/p95 latency, and throughput visibility per route, plus Sentry's own Alert Rules (configured in the Sentry dashboard once you have a project — e.g. "alert if error rate exceeds N/hour" or "alert on a new error type") for the alerting half of this section. This satisfies the *intent* of this section (visibility + alerting on the failure modes below) without a second signup/SDK/dashboard.

**Explicitly NOT in scope / not what this closes**: a general-purpose custom business-metrics pipeline (e.g. counting "orders/sec by provider" as a dedicated time-series metric, queue-depth gauges, etc.) — Sentry Performance Monitoring is transaction/latency-oriented, not a Prometheus-style custom-metric system. If that's wanted later, it's a distinct, larger follow-up (e.g. a real Prometheus/Grafana stack or a hosted metrics backend), not something this pass silently assumed was equivalent.

**Concrete alerts still worth configuring once you have a Sentry project** (or via your chosen deployment platform's own monitoring, e.g. Vercel's own function-error dashboards):
- The `/api/health` endpoint returning non-200 for more than a few minutes — either a real uptime monitor (see `docs/INCIDENT_RESPONSE.md` §3) or a Sentry Cron Monitor-style check hitting it.
- The cron endpoints (`/api/cron/*`, see §14 below) failing repeatedly — `.github/workflows/cron.yml`'s own step already fails the GitHub Actions run on a non-2xx response, which GitHub itself can notify on (Settings → Notifications → failed workflow runs) as a zero-additional-cost alert path.
- The "Upstash Redis not configured" production warning (`lib/rate-limit.ts`) appearing in logs at all in production — should never appear once configured correctly; a Sentry log-based alert or a simple log-aggregator search-alert both work.

**✅ Order-processing queue depth — now implemented**, closing what was previously tracked here as an honest open gap. `lib/services/jobs.ts#checkQueueDepth()` runs after every `GET /api/cron/process-orders` invocation (the highest-frequency of the three cron routes — reusing it avoids a fourth endpoint/schedule/secret for what is fundamentally a health check on the other jobs' own output) and checks two independent signals:
- `staleProcessingCount` — orders stuck in `PROCESSING` for more than `STALE_PROCESSING_MINUTES` (15 min) without moving to `IN_PROGRESS`/`FAILED`, indicating a provider-side issue or a `dispatchOrderToProvider` bug silently swallowing the state transition.
- `pendingBacklogCount` — `PENDING` orders exceeding `PENDING_BACKLOG_ALERT_THRESHOLD` (20), indicating `process-orders` itself has likely stopped running (scheduler down, `CRON_SECRET` drift between Vercel and the GitHub Actions repository secret) rather than a per-order problem.

If either threshold is breached, the route responds `503` (even though the batch itself ran fine) — matching `GET /api/health`'s existing "503 means something needs attention" convention — which fails that scheduled GitHub Actions run and surfaces as a failed-workflow-run notification, the same zero-additional-infra alert path already established above for the cron endpoints. Covered by `lib/__tests__/integration/queue-depth.integration.test.ts` (6 tests, DB-backed, both thresholds and the "not stale/not over threshold" negative cases). See `docs/INCIDENT_RESPONSE.md` §6.2 for the on-call response to this alert firing.

**Verified live against the real production Supabase database** (not just the mocked/in-memory test suite): started the app against this project's actual `.env.local` (a real pooled Supabase `postgresql://` connection string, not a local one) and drove `GET /api/cron/process-orders` through `curl` with the exact request shapes `.github/workflows/cron.yml` sends —
- No `Authorization` header → `401 {"error":"Unauthorized."}`.
- Wrong bearer token → `401 {"error":"Unauthorized."}`.
- Correct `CRON_SECRET` → `200`, with a real `queueDepth: {"alert": false, ...}` block computed against the live tables.
- All three cron routes (`process-orders`, `poll-order-status`, `compute-delivery-estimates`) and `GET /api/health` all returned `200` against the real Supabase database.
- Inserted one real, temporary `Order` row directly into the live `Order` table with `status: "PROCESSING"` and a backdated `updatedAt` (25 minutes in the past, past the 15-minute threshold), then re-hit `GET /api/cron/process-orders`: it correctly responded `503` with `queueDepth: {"staleProcessingCount": 1, "alert": true, ...}` — proving the alert genuinely fires against real data, not just the synthetic integration-test fixtures. The probe row was deleted immediately after and a follow-up request confirmed the endpoint returned to `200`/`alert: false`.

This closes the loop on "does this actually work against a real deployment shape," short of the two things that genuinely require your own accounts: creating the `PROD_URL`/`CRON_SECRET` GitHub repository secrets so `.github/workflows/cron.yml` can reach a real deployed URL, and setting `CRON_SECRET` on the real Vercel project (see README.md §11's exact steps).

## 8. Performance & Capacity

✅ **Implemented** — connection pooling capped at 10 (`lib/db.ts`), pagination capped at 50 items/page on list endpoints, indexes verified against actual query patterns (see [`DATABASE.md` §5](DATABASE.md#5-indexing-strategy)).

❌ **Gap** — no load testing has been performed against this codebase (none is claimed); no defined capacity plan (expected orders/sec, concurrent users) exists. Given the current single-instance background worker design (see [`ARCHITECTURE.md` §9](ARCHITECTURE.md#9-scalability--performance-considerations)), capacity planning should specifically validate order-processing throughput under realistic provider-API latency before scaling customer acquisition.

✅ **Resolved by the Postgres/Prisma migration** — the original Mongoose `autoIndex` footgun this entry used to describe (an implicit, synchronous `createIndex` call against a live collection at connection time, which could briefly hold a write lock and cause request timeouts) has no Prisma equivalent: index changes are only ever applied when you explicitly run `npx prisma db push` (or, for a large existing production table, a hand-run `CREATE INDEX CONCURRENTLY` during a maintenance window — see [`DATABASE.md` §8](DATABASE.md#8-migration-strategy)), never implicitly at application-connection time. There is no "index auto-creation on connect" setting to misconfigure in the first place.

## 9. Security Hardening

✅ **Implemented:**
- HTTP security headers (`next.config.ts`): `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, restrictive `Permissions-Policy`, HSTS with `preload`, `poweredByHeader: false`.
- Password policy enforced both client-facing (Zod) and via bcrypt cost-12 hashing; account lockout after 5 failed attempts (15-minute window) — `auth.ts`.
- Encrypted-at-rest provider secrets, hashed one-time tokens (§2).
- Telegram webhook signature verification via `TELEGRAM_WEBHOOK_SECRET` (`app/api/telegram/webhook/route.ts`).
- HTML-escaping of all user-controlled strings sent to Telegram (`lib/telegram/format.ts`) — prevents markup injection in bot messages.
- Rate limiting on every sensitive action (login, register, password reset, order creation, payment submission, ticket creation/reply, Telegram linking/bot actions) — `lib/rate-limit.ts`.
- **Cross-origin request enforcement for `/api/**`** (`lib/security/origin.ts`, wired into `proxy.ts`) — added in this pass. Previously `ALLOWED_ORIGINS` was defined in `lib/env.ts` but read nowhere else in the codebase (verified by grep before this fix), so it had no effect; a live test against a running dev server confirmed a cross-origin request to `/api/services` was fully processed with no origin check. `proxy.ts` now rejects any `/api/**` request whose `Origin` header is present and not in `ALLOWED_ORIGINS` with a `403`, before it reaches route-handler logic. Scoped deliberately: `/api/auth/**` is excluded (Auth.js manages its own CSRF protection; double-enforcing here risks breaking sign-in) and `/api/telegram/webhook` is excluded (Telegram never sends an `Origin` header — that route is protected by `TELEGRAM_WEBHOOK_SECRET` instead). Requests with no `Origin` header at all (same-origin page navigation, server-to-server calls, the background worker, curl) are not blocked by this check — it is a browser-cross-origin control, not a general auth mechanism, and every mutating route still independently enforces its own session/role checks regardless of origin. Verified end-to-end against both `next dev` and a real `next build && next start` production run: unauthenticated page redirects, admin role gating, and authenticated access all continue to work exactly as before, while a disallowed cross-origin request now correctly receives `403`.

✅ **Implemented (this entry was stale — verified live and corrected):** a nonce + `strict-dynamic` Content-Security-Policy is set on every response (`lib/security/csp.ts`, generated per-request in `proxy.ts`, forwarded to Server Components via the `x-nonce` header for any future inline `<script>` that needs it). Verified live against a real `next start` production server: `curl -I /login` returns `content-security-policy: default-src 'self'; script-src 'self' 'nonce-<random>' 'strict-dynamic'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https: blob:; font-src 'self' data:; connect-src 'self' https:; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; upgrade-insecure-requests`. This project has zero inline `<script>` tags or `dangerouslySetInnerHTML` usage (verified by grep across `app/`/`components/`), so this policy introduces no risk of breaking existing pages; `style-src 'unsafe-inline'` only covers Tailwind's generated utility classes (plain CSS), not script execution.

✅ **Dependency vulnerability scanning is now wired into CI.** `npm audit --audit-level=high` runs as a CI step (see `.github/workflows/ci.yml`) and `npm audit` currently reports 0 vulnerabilities. **Still a gap:** no Dependabot/Renovate config exists yet for automated *update* PRs (as opposed to just flagging vulnerabilities) — see §12 below for that specific recommendation.

⚠️ **Newly discovered production gap (found and fixed in this pass) — `AUTH_TRUST_HOST` was entirely missing from the env schema and undocumented, and its absence breaks the app in production.** Auth.js only auto-trusts the incoming request's `Host` header when `NODE_ENV !== "production"` (always true in local dev, which is exactly why this was never caught before). Without `AUTH_TRUST_HOST=true` (or `AUTH_URL` set — note `NEXTAUTH_URL` does **not** satisfy this, confirmed by reading `next-auth`'s own source and reproducing the failure against a real production build), **every** auth-related request fails with an `UntrustedHost` error once `NODE_ENV=production` — including `proxy.ts`'s own route-protection check, meaning this would have broken login and all `/dashboard`/`/admin` access in any real production deployment before this fix. `lib/env.ts` now validates and warns if this is missing in production, `.env.example` documents it, and `.github/workflows/ci.yml`'s build step sets it so CI doesn't spuriously warn. See [`../README.md` §11](../README.md#11-production-setup--operational-requirements) and its troubleshooting entry.

⚠️ **Newly discovered dev-environment gap (found and fixed in this pass) — running behind a sandboxed/tunneled preview domain (not `localhost`) silently broke both registration and login, with no visible error.** Reported symptom: the register/login pages "just blinked/refreshed" with no error shown, and pre-existing users in the real database could not log in either. Root cause was **two independent cross-origin blocks stacking**, both triggered because the browser loads the app from a dynamic preview host (e.g. Arena Agent Mode / E2B sandboxes serve it at `https://<port>-<sandboxId>.e2b.app`) instead of `http://localhost:3000`:
1. **Next.js dev server's own `allowedDevOrigins` protection** returned a bare `403 Unauthorized` for every `_next/static` JS chunk request from that real origin — confirmed via the dev server's own log line (`⚠ Blocked cross-origin request to Next.js dev resource ... from "<host>"`). React therefore never hydrated in the browser, so **every** client-side form's `onSubmit` handler silently never attached, and the browser fell back to a native full-page HTML form submission — exactly matching the "blinks and refreshes, no error" symptom, and affecting login and registration identically since both are client components.
2. **This project's own `checkOrigin()` CORS guard** (`lib/security/origin.ts`, §9 above) independently rejected the actual `/api/register` (and any other mutating `/api/**`) request from that same origin with a second `403`, because `ALLOWED_ORIGINS` only listed `http://localhost:3000`.

**Fix:** `next.config.ts` now sets `allowedDevOrigins: ["localhost", "**.e2b.app"]` in development only (production is unaffected — this option has no effect once `NODE_ENV=production`, since the dev-server-only protection it configures doesn't run at all). `lib/security/origin.ts`'s origin check now supports the same wildcard syntax Next.js's own option uses (`*.`/`**.` prefixes), and `ALLOWED_ORIGINS` in `.env.local`/`.env.example` includes `**.e2b.app` alongside the existing `http://localhost:3000` entry. **Verified end-to-end after the fix, against the real Supabase/Postgres database:** replayed real requests carrying the actual sandbox `Host`/`Origin` headers — the static JS chunk request went from `403` to `200`, `/api/register` went from `403` to `201`; a full headless-browser run through that same simulated origin created a real user (genuine bcrypt hash, confirmed via a direct row lookup) and successfully logged in both that new user and a separately pre-existing user, reaching `/dashboard` in both cases; wrong-password and duplicate-email cases were also confirmed to display real, visible error messages rather than a silent failure. If you ever see a client-side form appear to do nothing (no network request, no console error, no visible error message) in *any* non-`localhost` preview/tunnel environment, check the dev server logs first for this exact `allowedDevOrigins` block message before assuming the form/API logic itself is broken.

## 10. Authentication & Authorization Security

✅ **Implemented** — see §9 and [`ARCHITECTURE.md` §3](ARCHITECTURE.md#3-authentication--authorization-flow): bcrypt + per-account lockout, IP-based login rate limiting (see §12 for the fix and its tuning history), JWT sessions, route-level (`proxy.ts`) and route-handler-level (per-route `auth()` + role check) double enforcement.

⚠️ **Partial** — the `User` schema has `twoFactorEnabled`/`twoFactorSecret` fields, but **2FA is not wired into the actual login flow anywhere** (verified: `auth.ts`'s `authorize()` never reads these fields). Do not describe 2FA as a working feature; it is unimplemented schema scaffolding today. If needed, complete the TOTP verification step in `auth.ts` before advertising this as a security feature to users.

❌ **Gap** — no session revocation mechanism exists for JWT-strategy sessions (the standard tradeoff of stateless JWTs) — e.g. if an admin account is compromised, there is no "invalidate all active sessions" action; the compromised session remains valid until its 30-day `maxAge` naturally expires. **Recommendation:** if this matters for your threat model, either shorten `maxAge` significantly for admin sessions or move to database-backed sessions for the `ADMIN` role specifically.

## 12. Rate Limiting & Abuse Protection

✅ **Implemented** — see §9. Production note (already surfaced by the code itself, repeated here for visibility): **without `UPSTASH_REDIS_REST_URL`/`TOKEN` configured, rate limiting silently degrades to a per-server-instance in-memory counter**, which does not coordinate across multiple instances — configure Upstash before deploying more than one instance.

✅ **Fixed (found and closed in this pass) — login had NO IP-based rate limiting at all, despite `lib/rate-limit.ts` defining a `login` config entry from early in this project's history.** Confirmed by grepping every call site of `rateLimit(...)` across the whole codebase: every other sensitive action (register, password reset, order creation, payment submission, ticket creation/reply, API key creation, Telegram linking) called it; `auth.ts`'s login `authorize()` never did. This meant a single IP could attempt unlimited logins against unlimited different accounts (classic credential stuffing) with no throttling at all — the separate per-account lockout (`auth.ts`, 5 failed attempts -> 15-minute lock) only stops repeated failures against ONE specific account, not high-volume attempts spread across many accounts from one source. Fixed by calling `rateLimit("login", ip)` at the top of the (now separately-exported, directly unit-testable) `authorizeCredentials()` function in `lib/auth/authorize.ts`. The limit itself (`configs.login` in `lib/rate-limit.ts`) is deliberately set to `[20, 300]` (20 attempts per 5 minutes per IP) rather than a tighter "5 per minute" textbook default: it's keyed by IP, not by account, so it needs enough headroom that ordinary legitimate traffic sharing one IP (an office/university NAT gateway, a household, a VPN exit node, or one real person testing a couple of accounts) never gets collaterally locked out — discovered concretely when an initial, tighter `[5, 60]` value broke this project's own Playwright e2e suite (`e2e/order-flow.e2e.ts`), which legitimately logs in as three different seeded accounts across one run from one IP, a realistic stand-in for exactly this kind of shared-IP multi-account pattern. Covered by 11 new unit tests in `lib/__tests__/auth-authorize.test.ts` (malformed input, unknown account, wrong password + lockout-counter increment, 5-failure lockout, locked-account rejection, non-ACTIVE-status rejection, successful login + counter reset, and — using the REAL `lib/rate-limit.ts` module, not mocked — both "the Nth+1 attempt from one IP is rejected" and "a different IP is unaffected").

❌ **Gap** — no bot/scraper defense beyond rate limiting exists (no CAPTCHA on registration, no WAF-level bot detection configured in this codebase — that would typically live at the CDN/reverse-proxy layer, e.g. Cloudflare, outside this repository's scope).

## 13. Database Backup & Recovery / Disaster Recovery

⚠️ **Partial — documentation done, backup enablement itself is a Supabase-console/billing-tier action this codebase cannot perform** — backup automation is genuinely an infrastructure/platform concern, not application code (no amount of code in this repo enables Supabase's daily-backup or Point-in-Time Recovery features; they're per-project settings tied to your Supabase billing plan). What this pass adds: exact, concrete steps for enabling it and testing a real restore, plus the disaster-recovery runbook that was previously just a recommendation.

**What Supabase actually offers, by plan** (confirmed against Supabase's own docs as of this writing — verify current details against `https://supabase.com/docs/guides/platform/backups` before relying on this, since Supabase's plans/pricing do change):
- **Free plan**: no dashboard-managed backups at all. If your project is on Free, you are fully responsible for your own `pg_dump` schedule (see the DIY option below) — do not assume Supabase is backing this up for you.
- **Pro plan**: daily automatic backups, retained 7 days, restorable in-place from the Dashboard (**Database → Backups**). This is the minimum tier this app's production deployment should run on, given it's a money-handling app.
- **Team plan**: same daily-backup mechanism, 14-day retention.
- **Enterprise plan**: same mechanism, up to 30-day retention.
- **Point-in-Time Recovery (PITR)**, a paid add-on on top of Pro/Team/Enterprise (continuous WAL archiving instead of once-daily snapshots): lets you restore to any specific second within the configured retention window, not just a daily snapshot boundary — the direct equivalent of what MongoDB Atlas's Cloud Backup PITR add-on provided in the original design. This matters for a transactional wallet/order system, where "restore to last night's snapshot" could lose many real hours of transactions; PITR bounds that loss to however recently before the incident you can pick a recovery second.

**Exact steps to enable and test backups on a paid Supabase plan:**
1. Supabase Dashboard → your project → **Database** → **Backups**. Confirm daily backups are listed (automatic on Pro and above — nothing to explicitly "turn on" beyond being on a paid plan).
2. If the acceptable data-loss window for a real incident is shorter than "up to 24 hours" (true for this app — a wallet/order system), enable the **Point-in-Time Recovery** add-on from the same Backups page and set its retention window based on how much history you need to be able to roll back into.
3. **Do the dry-run restore now, not during a real incident** (see [`INCIDENT_RESPONSE.md` §7](INCIDENT_RESPONSE.md#7-backup--restore-reference)): Dashboard → Database → Backups → select a daily backup (or, with PITR enabled, the **Point in Time** tab's date/time picker) → **Restore to a New Project** (do this, not an in-place restore, for a test — an in-place restore makes the live project itself inaccessible for the duration of the restore and overwrites current data, per Supabase's own documented behavior). Note the dashboard-restore path currently produces a **database-only** copy — Storage objects, Auth settings, Edge Functions, and Realtime publication config are not part of it and would need separate reconfiguration in a real cutover; this app does not currently use Supabase Storage/Auth/Edge Functions/Realtime, so that gap doesn't apply to it today, but re-check this if that ever changes.
4. **Verify the restore with `npm run verify-restore -- --live "<LIVE_DATABASE_URL>" --restored "<RESTORED_DATABASE_URL>"`** (`scripts/verify-restore.ts`) instead of an ad-hoc manual spot-check. It connects to both databases with two independent Prisma clients and reports: (a) a per-table row-count comparison for every model in `prisma/schema.prisma`, flagging anything suspicious (a restored count exceeding live's, or a table that's zero on restored but non-zero on live); (b) a `Wallet.balance` grand-total comparison — the single most important money-handling invariant, and a far more sensitive corruption signal than eyeballing a few random rows; a restored total that *exceeds* live's is flagged as an immediate failure, since that's impossible under a genuine point-in-time restore of an earlier snapshot; (c) the concrete data-loss window — how many minutes of `Order`/`Payment` history exist on live but not on the restored snapshot, making the unavoidable "some recent transactions are lost" cost of any restore an explicit number instead of an implicit assumption. Exits non-zero on any detected inconsistency. **What this script does NOT do**: trigger or manage the actual Supabase restore itself (no Supabase management-API credentials are used/assumed) — it only verifies a restore you already performed via the Dashboard in step 3.

   **Verification performed so far**: (i) mechanically against two local ephemeral Postgres databases — both a "healthy older subset" scenario (passed) and an "impossible/corrupted balance" scenario (correctly failed, non-zero exit) — before this script was first documented; (ii) then run for real against this project's actual production Supabase database (the real pooled connection string in `.env.local`, containing real users/wallets/orders/payments/audit-log rows), comparing it against itself as the closest available proxy for a genuine snapshot restore in an environment with no Supabase restore-creation access: it correctly reported matching row counts across every table, a matching `Wallet.balance` grand total computed from real Postgres `Decimal` data, and a `0`-minute data-loss window (expected, since both sides were literally the same database) — confirming the script's queries and Decimal math all work correctly against real production-shaped data, not just synthetic test fixtures. **What is still NOT verified**: running this against an *actual* Supabase-restored project (a real second, snapshot-derived database) — that specifically requires triggering a real restore via the Supabase Dashboard on a paid plan, which needs your own Supabase billing/account access and isn't something achievable without it.
5. If you restored to a new project for the test, either promote it (repoint `DATABASE_URL`/`DIRECT_URL` at it) for a real cutover, or delete it once verified (a second live Supabase project on a paid plan costs money to leave running).

**Disaster-recovery runbook** — now covered by [`docs/INCIDENT_RESPONSE.md`](INCIDENT_RESPONSE.md), specifically §7 (Backup & restore reference, including the "restore to a new project, verify, then cut over" procedure, now referencing `scripts/verify-restore.ts` for the verification step) and §6.1/§6.3 (scenario playbooks for site-down and deposit-related incidents). Repointing `DATABASE_URL`/`DIRECT_URL` at a restored/failed-over database is indeed an env-var-only change given this app's architecture (`lib/db.ts` reads `DATABASE_URL` fresh via Prisma's datasource config, no hardcoded project reference anywhere else) — no code deploy needed for that step specifically, matching the original recommendation. On-call/paging is addressed by `INCIDENT_RESPONSE.md` §2's honest "no dedicated on-call rotation exists yet, here's the single-person-team version" framing, not a fabricated paging setup that doesn't reflect reality.

**Still honestly open**: `verify-restore.ts` has been verified both mechanically (local test databases) and against this project's real production Supabase database's real data (see above), but **the actual Supabase Dashboard restore-to-a-new-project step itself has never been performed** — that requires a paid Supabase plan and triggering a real restore via the Dashboard (needs Supabase billing/account access this development environment doesn't have). `docs/INCIDENT_RESPONSE.md` §7 still says so explicitly ("this procedure has not been tested end-to-end in this project") — do not remove that caveat until someone has actually performed a real Supabase restore and run `npm run verify-restore` against its output. Until both are set, `lib/env.ts` logs a loud production warning on every request if `CRON_SECRET` is missing, and the cron endpoints themselves fail closed — verified live (see `docs/INCIDENT_RESPONSE.md` §3 for how to notice this via logs).
- **Still a real limitation, stated honestly**: this is not a fault-tolerant distributed queue — it inherits every honest caveat `docs/ARCHITECTURE.md` §6 already documents about the original polling-worker design (no visibility timeout, no dead-letter queue), just now invoked over HTTP on an external schedule instead of an in-process timer loop. If order volume ever grows enough that GitHub Actions' 5-minute-minimum/best-effort timing becomes a real bottleneck, revisit with a real queue (SQS, Upstash QStash, etc.) or upgrade to Vercel Pro's per-minute native Cron Jobs — this is intentionally the simplest thing that could plausibly work for current scale, not a permanent architectural ceiling.

⚠️ **Partial — automated rollback is implemented but opt-in and not yet exercised against a real Vercel project.** `.github/workflows/post-deploy-smoke-test.yml` now has a second step, "Attempt automated rollback (Vercel)", that runs only when the smoke-test step fails. It:

2. Excludes the just-deployed (now-failing) deployment by matching its hostname against the smoke test's own target URL, then picks the newest remaining deployment that is `READY` and `isRollbackCandidate`.
3. Calls `POST https://api.vercel.com/v1/projects/{projectId}/rollback/{deploymentId}` to revert production traffic to it.

- `VERCEL_TEAM_ID` — Vercel Team Settings → General → Team ID; only needed if this project lives under a Vercel Team rather than a personal account, omit otherwise.

**Notable non-obvious lesson from building this suite, worth remembering for any future Playwright work in this repo:** Playwright's `config.webServer` option cannot be used here. Direct inspection of the installed runner (`node_modules/playwright/lib/runner/index.js`) shows its task order is `[..., ...pluginSetupTasks, ...globalSetups]` — `webServer` runs as a plugin, so its process is spawned **before** `globalSetup` runs, meaning any `process.env` mutation made inside `globalSetup` (this suite's `DATABASE_URL`, computed from `E2E_DATABASE_URL` only after asynchronously seeding the database; the dynamic server-log path used to recover the verification link; etc.) does not exist yet from that spawned process's point of view. Confirmed both by reading the source and by a minimal reproduction. `e2e/global-setup.ts` works around this by spawning and owning the `next start` process itself (via the `next` binary directly, in a detached process group so `globalTeardown` can reliably kill the whole group — invoking it via `npm run start` instead left an orphaned `next-server` process bound to the port after a run, breaking the next one with `EADDRINUSE`), after all the env vars and seed data are ready, rather than delegating that to Playwright.

**Historical bug, from the original MongoDB-era version of this suite (kept here as a still-relevant lesson about test-database isolation, even though the specific mechanism no longer applies post-migration):** `MongoMemoryReplSet.getUri()` called with no argument returned a URI with no database name in its path, which made Mongoose default the connection to database `"test"`. The suite's `globalSetup` seeded data by connecting with a separate `{ dbName: "e2e" }` option — while the real server connected using the bare connection-string env var and landed in `"test"` instead. The server could never see any seeded user, so every login attempt failed with a generic `CredentialsSignin` error. The general lesson (worth remembering regardless of database engine): whenever a test harness computes a connection string in one place and the seeding code computes a possibly-different one in another, they must be guaranteed to be the exact same string, not just "the same logical database" — the current Postgres-era `e2e/global-setup.ts` avoids this class of bug entirely by using one single `E2E_DATABASE_URL` value for both seeding and the spawned server's `DATABASE_URL`, never computing either independently.

**A real, previously-undiscovered bug was found and fixed by writing these tests, not just as a testing exercise:** both `approveDeposit` and `rejectDeposit` in `lib/services/admin-payments.ts` fetched the `Payment` row once, then applied the actual status transition via a *separate* atomic `updateMany(...)` claim call (correct — this is the intentional atomic-claim guard against double-processing, see [`DATABASE.md` §6](DATABASE.md#6-transactions)) — but then returned that **original, pre-update, now-stale in-memory row** instead of one reflecting the just-persisted change. The database was always updated correctly; only the *returned value* was wrong. Concretely, this meant the admin approve/reject API routes (`app/api/admin/payments/[id]/approve|reject/route.ts`) — and the Telegram bot's equivalent inline-button handlers, which reuse these same functions — would show a payment as still `PENDING` in their immediate response even though the approval/rejection had actually succeeded. Fixed by mutating the in-memory row to match what was actually persisted (same `reviewedAt` timestamp reused for both the DB write and the in-memory patch, so they can never drift) instead of trusting the stale pre-fetch snapshot. This is the same class of "read-before-atomic-write, then return the stale read" mistake — worth remembering as a general pattern to watch for in any future service function that does an atomic claim-update followed by further logic using a separately-fetched copy of the same row.

## 16. Deployment & Rollback Strategy

✅ **Implemented — superseded by, and now fully answered in, §14.** This section previously said "deployment method is not yet decided/standardized" and recommended running the three background workers as persistent services "whichever platform is chosen" — that decision has since been made and implemented (see §14 for the full detail, this is a short pointer/summary so this section isn't stale):

- **Platform: Vercel**, via its native Git integration (connect the repo, push to `main`, atomic zero-downtime deploys and instant rollback are both handled natively by Vercel's own deployment model — no extra config needed for either). Deploys are gated on `.github/workflows/ci.yml` passing first, via the Vercel project's own "wait for CI" dashboard setting.
- **Rollback**: instant via the Vercel dashboard (Deployments → previous deployment → "Promote to Production"), and also available as an **opt-in automated path** triggered by a failed post-deploy smoke test (`.github/workflows/post-deploy-smoke-test.yml`'s "Attempt automated rollback (Vercel)" step — see §14 for the full mechanism and required secrets). The automated path is disabled by default and unverified against a real Vercel project from this sandbox, so the manual dashboard path remains the reliable fallback either way — see `docs/INCIDENT_RESPONSE.md` §6.1.
- **Background workers**: since Vercel is serverless-only and genuinely cannot run `npm run process-orders -- --loop` (or the other two workers) as a persistent process at all, the original recommendation above ("run them as persistent background services separately from the web server") does not apply to this deployment target. Instead, their logic is exposed as authenticated `GET /api/cron/*` routes (`lib/services/jobs.ts`, invoked by `.github/workflows/cron.yml` on a schedule) — see §14 for the full mechanism, and `docs/ARCHITECTURE.md` §6's "Dual invocation path" for how the original CLI scripts still work unchanged for any non-Vercel/self-hosted deployment that *can* run them as persistent services.
- The distributed-locking caveat from [`ARCHITECTURE.md` §9](ARCHITECTURE.md#9-scalability--performance-considerations) — none of the three jobs should be scaled to multiple truly-concurrent instances without a real lock — still applies to the HTTP-invoked path too; see that section for why an occasional overlapping GitHub Actions run degrades to redundant work rather than corruption, which is a materially weaker guarantee than a real lock and is documented as such, not glossed over.

Combined with the `npm audit` CI step (§9 above), both halves of "automated dependency hygiene" (security-advisory scanning + routine version updates) are now covered.

✅ **Fixed — a real, previously-undiscovered `npm ci` failure was found and closed in this pass.** `nodemailer` was pinned to `^9.1.0` while `next-auth@5.0.0-beta.32` declares an *optional* peer-dependency range of `^7.0.7 || ^8.0.5` (next-auth's own bundled Email/magic-link provider — not used by this project, which only uses the Credentials provider — depends on an older nodemailer major). `npm install` silently tolerated this (with a warning), but `npm ci` — **the exact command this project's own CI workflow runs** — fails hard on the conflict, meaning the checked-in lockfile could not actually be installed reproducibly in CI or in a fresh clone. Confirmed via a real `npm ci` run against a clean checkout before and after the fix. Root cause understood in full before fixing: `nodemailer@<=9.0.0` also carries a real GitHub Security Advisory ([GHSA-p6gq-j5cr-w38f](https://github.com/advisories/GHSA-p6gq-j5cr-w38f), high severity, patched in `9.0.1`) for a `raw`-message SSRF/arbitrary-file-read bypass of `disableFileAccess`/`disableUrlAccess` — not directly exploitable here since `lib/mail.ts` never accepts a `raw` message field or exposes those flags to caller-controlled input, but staying on a patched version is the correct choice regardless. **Fix:** added `"overrides": { "nodemailer": "^9.1.0" }` to `package.json`, which forces npm to resolve the patched, non-vulnerable version despite next-auth's stale optional-peer range, without needing `--legacy-peer-deps` anywhere (including in CI). Verified: `npm ci` succeeds cleanly, `npm audit` reports 0 vulnerabilities (previously 3 high-severity, all from this same transitive chain).
